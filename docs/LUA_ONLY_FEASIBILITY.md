# Lua-only identity feasibility

Project Version: 0.2.0-dev.12

**Complete native admission and automatic authenticated identity across restarts are not established through the inspected Lua interfaces.** This is a bounded negative result for the current design and Build 42.21 evidence, not a universal mathematical proof that every possible Lua-only design is impossible. No custom Java, class replacement, injected code, bridge or native binary is permitted.

## Exact missing boundaries

| Native operation | Present obstacle | Can a managed-only restriction close it today? |
| --- | --- | --- |
| Generic factory/load and VirtualAnimal re-entry | Restores/inserts body without any of nine action completions | No certified per-type pre-admission veto found; restart/streaming are inherent to a world animal |
| Animal item load and forced native drop | Native parser creates embedded body; native heavy-item drop calls reconstruction directly | Blocking selected pickup/drop completions reduces normal paths, but full upstream cut including existing/imported items is unproved |
| Trailer/vehicle/hutch save load | Reconstructs contained animals outside manual completions | Refuse current manual managed transfers; preferences alone cannot exclude serialized contents/admin paths |
| Native growth | Replaces body, reuses N, no demonstrated ModData transfer/transaction | Current single stage/no nextStage limits ordinary automatic growth; forced callers and effective definitions still require proof |
| Corpse/reanimation | Copies public metadata into another body, new native integer | Refuse authorization and automatic revival; terminal private transaction still absent |
| Previous session | No proved final native-save/quiescence seal, public tokens replayable | Current-process latch/journal after detection cannot close unobserved prior import/save/crash |

Evidence and reachability qualifications are in [coverage](NATIVE_ADMISSION_COVERAGE.md) and [session integrity](PREVIOUS_SESSION_INTEGRITY.md). Client-side constructor sites are not automatically server ingress vulnerabilities. Conversely, lack of an ordinary client UI path is not security closure.

## Narrower lifecycle proposal

The smallest research candidate is one server-created adult, world-only carrier; no pickup, inventory conversion, trailer, vehicle, hutch, breeding, growth or resurrection. No population-based auto-adoption. Missing/offscreen means unavailable with private record retained. Ordinary carry/trailer consumers stay blocked. Death must become terminal through an independently proved private transaction before supported gameplay. This is **proposed scope, not certified support**. Native world load/streaming and previous-session provenance remain unresolved even under this restriction, so ownership stays disabled.

The present safe usable slice is narrower still: explicit disposable-world provisioning, private logical record recovery and native **diagnostics with no companion authority**. It can report what was loaded and safely refuse ambiguous matches. This does not meet the user's final same-legitimate-dog requirement; no “save/load working” claim follows.

A separate operator-mediated re-association workflow could preserve logical history after restart without claiming automatic physical continuity. It would require a reviewed contract change, explicit operator responsibility, immutable reconciliation evidence and no silent creation. It is a proposal only. A purely logical dog without a persistent native body would also change scope and is not substituted here.

## Next smallest safe step

Prove one exclusive Lua-visible server genesis/admission boundary plus a previous-session binding strategy on the pristine supported game, including generic deserialize and worker return paths. If those seams cannot be proved, report the exact limitation and obtain a scope decision between continued diagnostics and explicit reconciliation. Do not add gameplay writers, increment native integers, trust public signed markers, or disable checks to obtain a visual success. Runtime negative tests can proceed only under separately authorized test setup; positive ownership continuity remains blocked until the design obligations are met.
